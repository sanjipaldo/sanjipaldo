# Claude 작업 규칙 — DOOGO FOOD DB CENTER

이 파일은 Claude Code/Claude에게 프로젝트를 넘길 때 가장 먼저 읽히는 운영 지침입니다.

## 1. 프로젝트 개요

- 서비스: 두고푸드 공개 상품 DB 및 관리자 데이터센터
- 배포 버전: v63
- 공개 사이트: `https://doogofood.site/`
- 관리자 진입: `https://doogofood.site/admin`
- 기술 스택:
  - Client: React 19 + TypeScript + Vite + React Router
  - Server: Hono + TypeScript
  - DB: LibSQL/SQLite + Drizzle
  - 패키지 관리: pnpm workspace
- 프로젝트 형태: Skywork self-host full-stack Website

## 2. 작업을 시작할 때 반드시 읽을 파일

1. `CLAUDE_HANDOFF.md`
2. `AGENTS.md`
3. `.skywork/brief.md`
4. 수정 대상과 직접 연결된 파일

전체 프로젝트를 무작정 재구성하지 말고 기존 구현과 디자인을 유지하면서 요청 범위만 수정합니다.

## 4. 절대 지켜야 할 구현 규칙

- 공개 화면과 관리자 화면 모두 PC·모바일을 함께 수정합니다.
- 기존 확정 화면은 사용자가 요청하지 않은 범위까지 재디자인하지 않습니다.
- API 호출은 반드시 `apiFetch`를 사용합니다. UI 코드에서 직접 `fetch`, `axios`, `XMLHttpRequest`를 사용하지 않습니다.
- `/admin/*` 화면과 관리자 API 인증을 약화시키지 않습니다.
- `.skywork/website.json`, `.skywork/website/website.json`, `apps/client/public/app-config.js`를 직접 수정하지 않습니다.
- `apps/server/_core/*`는 플랫폼 핵심 코드이므로 일반 기능 작업에서 수정하지 않습니다.
- 기존 마이그레이션 파일을 수정하지 않습니다. DB 변경이 필요하면 다음 번호의 새 마이그레이션을 추가합니다.
- 비밀번호, API 키, DB 토큰을 코드·문서·로그에 넣지 않습니다.
- `git reset --hard`, 강제 checkout, 광범위 삭제를 하지 않습니다.
- 사용자 DB 데이터를 임의로 초기화하거나 샘플 데이터로 덮어쓰지 않습니다.
- 공개 사이트는 현재 일반상품 단일 모델입니다. 묶음상품/그룹상품 UI를 다시 활성화하지 않습니다.

## 5. 발주오라 연동 안전 경계

- 발주오라 공식 쓰기 API와 서버 전용 인증 계약이 확인되지 않았습니다.
- 계정 아이디/비밀번호만으로 연결 성공이나 상품 전송 성공을 가장하지 않습니다.
- 현재 기능은 외부 상품 ID, 변경 대기열, 전송 상태, 실패 사유를 관리하는 안전한 준비 단계입니다.
- 연결 방식(발주오라 오픈 API 개발 중): 관리자 > 발주오라 연동에서 몰 ID·API 키·API 주소(https://…baljuora.com만)를 등록합니다. API 키는 AES-GCM으로 암호화해 `integration_connections`에 저장하고 끝 4자리만 표시합니다(migration 021).
- "연결됨"은 등록한 API 주소가 API 키로 실제 2xx 응답했을 때만 표시합니다. 자동 동기화(데이터센터→발주오라, 발주오라→데이터센터) 스위치는 연결됨일 때만 켤 수 있으며, 실제 전송·가져오기 작업은 API 사양 공개 후 구현합니다.
- 공식 API 또는 서버 토큰이 제공되기 전에는 외부 상품 생성·수정·삭제를 실행하지 않습니다.
- 비밀번호 원문을 DB에 저장하지 않습니다.

## 6. 현재 상품 운영 규칙

- 공개 상품 상태는 `판매중`(검정 뱃지·흰색 행), `시즌 종료`·`품절`(뱃지 + 분홍색 행)으로 표시합니다. 품절·시즌 종료 행은 품절이슈 카드와 같은 흰색 → 연분홍 그라데이션(`--w-unavailable-gradient`: 135deg #fff → #fff4f5, 테두리 #f0d0d3, 진한 빨간 띠 없음)이며 단가표·신규상품·관리자 상품 리스트(PC 표·모바일 카드)가 같은 색을 씁니다. PC 표는 줄(tr)에 그라데이션을 주고 칸(td)은 투명하게, 관리자 표의 오른쪽 고정 "관리" 칸만 그라데이션 끝 색(#fff4f5)으로 채웁니다.
- 판매 상태는 판매중 / 품절 / 시즌종료 3가지입니다(migration 028: `products.isSeasonEnded` 칸 추가, 구조 변경만·기존 데이터 값 변경 없음). 판단은 공개·관리자 공용 `apps/client/src/lib/supply-status.ts`(`supplyStatus`) 한 곳에서 합니다: ① 품절(또는 옵션 전부 품절) → 품절, ② 관리자가 지정한 시즌종료 → 시즌종료(판매기간과 무관), ③ 제철 카테고리인데 이번 달(한국 날짜)이 판매기간 밖이거나 판매기간 미설정 → 시즌종료, ④ 나머지 → 판매중. 품절과 시즌종료는 동시에 켜지지 않습니다(서버에서 품절이면 isSeasonEnded=false로 저장). 상태를 보내지 않는 저장(일괄 변경 다른 항목·엑셀 반영)은 기존 isSeasonEnded를 그대로 둡니다.
- 관리자 상품 리스트도 공개 단가표와 같은 기준으로 품절·시즌종료 행을 분홍색 그라데이션 행으로 보여 주고, 상태 칸에 판매중/품절(슬레이트)/시즌종료(빨강) 뱃지를 둡니다(`tr.is-unavailable.is-sold_out|is-season_ended`). 선택 바 빠른 변경은 판매중·품절·시즌종료, "일괄 변경"의 판매 상태도 3가지 중 선택입니다. 상태 필터에 "시즌종료 상품"(`?status=seasonended`)이 있습니다.
- 사용방법(/how-to, 상단 메뉴 품절이슈 다음): /how-to → /how-to/supplier. "위탁셀러 | 공급사" 탭으로 각자의 랜딩페이지(`pages/catalog/UsageGuide.tsx`). 공급사 화면 = 하루 주문 처리 일정 · 입점 절차 · 주문 처리 방법 · 정산 안내(기준·주기·지급일·세금계산서·차감, 정산 예시) · 사용법 영상 · FAQ · 입점 신청 CTA. **공급사 거래 방식(관리자 확정 2026-11-07)**: 공급사에게 발주오라 공급사 계정이나 별도 관리자 사이트·프로그램을 주지 않습니다. 두고푸드가 입점 때 공급사와 정한 시간(오전 1회·오후 1회)에 공급사별 발주서(엑셀)를 메일로 보내고, 공급사는 출고 후 그 메일에 택배사·송장번호를 넣은 엑셀로 회신합니다(셀러 주문 → 발주서 메일 → 포장·출고 → 송장 회신 → 취소·반품·교환). 공급사에게 보이는 화면·제안서 PDF·영상에는 "발주오라"를 쓰지 않습니다. 위탁셀러 화면(/how-to/seller)은 아래 "위탁셀러 사용방법"을 봅니다. 운영 기준 11개(판매 수수료 포함)와 영상 목록(최대 30개, YouTube·Vimeo·mp4 주소)은 관리자 > "사용방법 관리"(/admin/usageGuide)에서 content_settings `supplier_guide`(JSON)로 저장하고, 빈 칸은 기본값(`packages/shared/src/supplier-guide.ts`, 서버·화면 공용)을 씁니다. 기본 운영 기준: 발주서 메일 발송 "평일 오전 1회 · 오후 1회 (입점 때 정한 시간)", 주문 마감 "각 메일 발송 직전까지 들어온 주문", 출고 "발주 메일을 받은 날 출고(늦어도 2일 이내)", 송장 회신 "출고 당일 오후 6시까지"(정산은 아래). 저장된 값이 예전 기본 문구(평일 오전 9시 30분 · 평일 오전 10시 전후 · 발주서를 받은 날 출고 · 예전 정산 문구 7개…)와 똑같거나 예전 기본 영상 목록(주소 없는 6편) 그대로면 화면·PDF에서 새 기본값으로 바꿔 보여 줍니다(`parseSupplierGuide`, DB 값은 바꾸지 않음, 관리자가 고친 문구는 유지). 운영 기준 값은 공급사 사용방법 화면에만 쓰이고, 입점 제안서 PDF에는 들어가지 않습니다(아래 제안서는 디자인된 고정 문서). 상단 메뉴가 8개라 1051~1279px에서는 메뉴 간격·글자를 줄여 한 줄에 맞춥니다.

- 가격변동 카드의 가격 칸(일반공급가·A단가·판매가)은 카드의 둘째 줄입니다. PC는 썸네일 오른쪽에 한 줄로, 모바일(720px 이하)은 단가표 모바일 카드처럼 카드 폭 전체의 2칸 표(칸마다 이름 → 새 가격 → 기존 가격·변동 금액, 칸 사이 구분선, 남는 칸은 한 줄 전체)로 보여 줍니다.
- 품절 표시: 단가표 품절 행(빨간 행)의 상태 뱃지와 최근 7일 품절 이슈 카드의 "품절"은 슬레이트 회색(#475569) 바탕·흰 글씨·금지(⊘) 아이콘(lucide `Ban`)으로, 썸네일 아래에 같은 회색 "품절" 띠를 겹쳐 보여 줍니다(빨간 행 위에서 빨강과 겹치지 않게). 품절 이슈 카드는 단가표와 같은 "배송 · 카테고리 · 배송비 · 판매기간" 줄과 오른쪽(모바일은 아래) 품절 날짜 "10.22(목)" + "오늘 품절/어제 품절/N일 전 품절"(한국 날짜)을 보여 줍니다.
- 공개 응답 크기: Vercel 함수 응답은 4.5MB를 넘으면 실패하고, 그러면 단가표가 처음 받은 10개 상품만 보여 줍니다. 그래서 단가표용 `/api/catalog`에는 최근 가격변동을 300줄까지만(필요한 칸만, 이미지·관리자 이름 제외) 싣고 `priceHistoryCount`(기간 안 전체 건수, "최근 변동" 숫자)를 함께 보냅니다. 가격변동 화면은 `GET /api/catalog/price-history`(최근 4일, 최대 5,000줄, 같은 가벼운 형식)로 따로 받습니다. 단가표는 전체 상품을 못 받으면 2·5·10초 뒤 다시 시도하고, 그래도 실패하면 "전체 상품을 아직 불러오지 못해 일부만 보이고 있습니다 · 다시 불러오기" 안내를 보여 줍니다. 공개 응답에 큰 데이터를 더할 때는 응답 크기를 먼저 확인합니다.
- "가격변동 엑셀 다운받기"(로그인 없이 누구나, `GET /api/catalog/price-changes/export?days=YYYY-MM-DD,…`, 오늘 포함 최근 4일만)는 고른 날짜 탭(전체면 4일)의 카톡 공지용 표를 내려받습니다(`services/price-notice-excel.ts`): 날짜마다 제목 행 + "상품명 | 기존/변동 A단가 | 기존/변동 일반공급가 | 비고". 같은 날 여러 번 바뀐 값은 처음→마지막 값으로 합치고 원래대로 돌아온 항목은 뺍니다. 인상·인하·변동(섞임)끼리 묶어 비고 칸을 합치고("단가 인상\n변경일 : 10월 22일(목)"), 그날 품절 상품은 아래에 모아 "품절\n품절시점 : …"으로 안내합니다. 원가와 지정 판매가 변동은 넣지 않습니다. 파일명 "1022 가격변동 공지.xlsx".
- 공개 "신규상품"(/new-products, 상단 메뉴 단가표 다음): 등록일(createdAt, 한국 날짜) 기준 최근 N일(기본 7일, 오늘 포함) 안에 등록된 공개 상품만 단가표와 같은 표(`CatalogProductTable`, 단가표와 공용)로 보여 줍니다. 등록일 탭(오늘·어제·N일 전·전체, 탭마다 개수, 처음에는 오늘 탭을 열고 선택한 탭은 연두색, 오늘에 상품이 없으면 "가장 최근 신규상품 보기" 버튼), "최근 7일 신규상품 N개 · 카테고리별 개수" 요약, 검색(상품명·상품코드·원산지), 국내/해외, 신규상품이 있는 카테고리 버튼(개수), 단가표와 똑같은 "월별 제철상품"(월 버튼·SEASON TIP·"N월 제철" 품목 키워드, 공용 `SeasonMonthFilter`, 신규상품 기준으로 계산), 상품마다 연두색 "NEW · 10.25(일) 등록 (오늘)" 뱃지, 페이지 번호. 최근 등록 순으로 정렬합니다. 단가표에서 숨김(미노출)인 상품은 보이지 않습니다.
- 관리자 > 상품 관리 > "신규상품 관리"(/admin/newProducts): 기간 안 신규 등록·신규상품에 보임·단가표 숨김·신규상품에서 제외 개수, 노출 기간(1~30일) 저장, 등록일 탭·검색, 상품별 "신규상품에서 빼기/다시 보이기". 설정은 content_settings `new_products`(JSON `{"days":7,"hidden":[상품 id…]}`, `PUT /api/catalog/admin/settings`, 서버에서 형식 검사)에 저장하며 마이그레이션이 필요 없습니다. 저장할 때 30일이 지난 상품 id는 hidden에서 정리합니다. 공용 계산은 `apps/client/src/lib/new-products.ts`. 클래스 이름에 Tailwind 유틸리티 이름(`fixed`, `invisible`, `hidden` 등)을 그대로 쓰지 않습니다(상태 클래스는 `is-…` 접두사).
- 원산지가 비어 있으면 원산지 안내를 표시하지 않습니다.
- 상품 노출순서는 `products.displayOrder`가 유일한 기준입니다.
- 관리자 진열순서 관리에서 드래그 앤 드롭과 위/아래 버튼을 모두 제공합니다.
- 공개 전체 목록과 카테고리 목록은 같은 진열순서를 사용합니다.
- 옵션 기능은 사용하지 않습니다. 발주오라 일반상품처럼 규격(중량·과수)마다 상품을 1개씩 등록하며, 상품코드로 발주오라 엑셀과 1:1로 맞춥니다(migration 019에서 기존 옵션을 독립 상품으로 분리).
- 신규 상품 등록(관리자 "신규 상품 등록"·API)은 상품코드가 필수이며 중복 코드는 저장하지 않습니다(발주오라·단가관리 코드와 1:1).
- migration 029는 관리자 요청(2026-11-03, "실제 운영 중이니 테스트 데이터 삭제")으로 넣은 1회성 데이터 정리입니다: 처음 설치 때 들어간 예시 데이터만 지웁니다 — 예시 소싱 요청(seed-sourcing-example, "제주 감귤 선물세트 5kg"·예시 셀러·010-0000-0000, 값이 그대로일 때만 삭제), 예시 가격변동 이력(sample-price-20260914-01~10 삭제), 예시 상품(muskmelon-gift 등 8개와 019에서 옵션을 나눈 opt-option-… 11개 중 예시 이미지 `/assets/products/…`를 그대로 쓰는 것만 숨김 + 삭제 표시, 관리자 "삭제"와 같은 방식). 관리자가 등록·수정한 실제 데이터는 바꾸지 않습니다.
- migration 026은 관리자 요청으로 넣은 1회성 데이터 수정입니다: 엑셀 대량 업로드로 DG 코드가 붙은 표고버섯 4개를 ass00057~ass00060으로 바꾸고 엑셀 순서로 진열순서를 맞춥니다(상품명·기존 코드가 맞고 새 코드가 비어 있을 때만).
- 새로 등록한 상품은 진열순서 맨 앞에 배치됩니다. 여러 상품의 공통 값은 상품 리스트의 "일괄 변경"으로 바꿉니다.
- 제철 월(판매기간)은 카테고리와 상관없이 저장·표시합니다(미분류 상품 포함). 제철 카테고리(농산·수산·축산·선물세트·식품)는 제철 월이 없으면 "판매기간 미설정/상품준비중", 그 밖의 카테고리는 제철 월이 없으면 "상시 판매"입니다.
- 목록의 "페이지당 보기 개수"는 선택 목록이 아니라 숫자 직접 입력입니다(`components/PageSizeInput.tsx`, 브라우저별로 마지막 값을 기억).
- 배송 정책은 발주오라 "배송비 정책 등록"과 같은 5가지 유형으로 관리합니다(migration 025, `services/shipping-rates.ts`·클라이언트 `lib/shipping-rates.ts`): 고정배송비(주문 금액에 관계없이), 배송비무료("이 정책 상품이 포함된 주문 전체 무료" 체크), 금액별·수량별·단위별(구간 "N 이상 ~ M 미만 → 배송비" + 추가/삭제, 마지막 "M 이상 → 배송비" + 조건 반복하기(켜면 발주오라처럼 마지막 줄 배송비 칸이 사라지고 "위 구간 반복 적용"으로 저장·표시), 단위별은 단위 선택). 정책명은 한글·영문·숫자(공백·_·-·괄호 가능) 20자, 배송비 코드는 영문·숫자 20자(비우면 SP+숫자 자동, 중복 불가), 제주/도서산간 추가배송비 있음/없음(있음이면 지역명 | 추가되는 배송비 표). 수정 창은 "배송비 정책 상세"(코드 읽기 전용, 삭제하기·저장하기). 금액 칸은 3,000처럼 쉼표로 보여 줍니다. migration 025 전 DB(운영 DB를 쓰는 미리보기)에서 저장하면 "운영 배포 후 저장" 안내가 나오고, 목록 읽기는 예전 칸으로 대신합니다. 국내/해외 배송유형과 택배사·반품/교환 배송비·설명(단가표 안내용)은 DB센터 전용 항목으로 유지합니다. 새 유형으로 저장하면 예전 칸(feeType·fee·feeBasis·무료 기준금액·feeLabel)도 함께 맞춰 둡니다. 예전에 만든 정책(rateType 비어 있음)은 저장된 값으로 유형을 추정해 보여 주고, 수정·저장할 때 새 유형으로 바뀝니다. 목록은 배송비코드·정책명·유형·대표 배송비·제주/도서산간·등록일시·적용 상품 수를 표로 보여 주며, 상품이 연결된 정책은 삭제할 수 없습니다. 단가표 "배송비" 버튼은 고정=그 금액, 구간형=첫 구간 배송비를 보여 주고, 팝업에서 구간을 줄마다 안내합니다.

## 6-0. 검색엔진 등록

- `apps/client/index.html`의 `naver-site-verification`, `google-site-verification` 메타 태그는 네이버 서치어드바이저·구글 서치 콘솔 소유 확인용입니다. 확인 후에도 지우지 않습니다.

## 6-1. 데이터 보관과 백업

- 운영 DB: Vercel Marketplace로 만든 Turso(LibSQL) `doogofood-db`, 지역 iad1(미국 동부). Vercel 함수도 iad1에서 실행되며, DB와 함수는 같은 지역에 둡니다(함수만 옮기면 DB 왕복이 길어져 오히려 느려짐).
- 상품 이미지: Vercel Blob `doogofood-images`(공개, `BLOB_READ_WRITE_TOKEN`).
- DB 백업: Vercel Blob `doogofood-backups`(비공개, `BACKUP_READ_WRITE_TOKEN`)의 `db-backups/`에 저장합니다.
  - 자동: `vercel.json` crons가 매일 18:00 UTC(03:00 KST)에 `GET /api/backup/cron`을 호출합니다(`CRON_SECRET` 필요, 운영 배포에서만 실행). 최근 30개만 보관합니다.
  - 관리자 > DB 백업: 목록·내려받기, "지금 백업 저장", "지금 내려받기"(저장소 없이 바로 파일 생성).
  - 형식: gzip JSON(`doogofood-db-backup` v1, 표별 columns/rows). 로그인 계정·세션(user, session, account, verification)과 `integration_connections`(발주오라 API 키)는 제외합니다.
  - 서버 코드는 `services/backup_storage.ts`(기본: 저장소 없음)를 쓰고, Vercel 빌드에서 `deploy/vercel/backup-storage.ts`로 바꿔 끼웁니다.

skywork-cli website validate --path reviewhub_catalog --gate local --progress-jsonl

pnpm lint

Skywork에서는 검증 성공 후 Website 배포와 Artifact 발행을 별도로 완료해야 사용자에게 새 버전이 전달됩니다.

### Claude Code(클라우드 컨테이너) 로컬 실행

`skywork-cli`가 없는 환경에서는 로컬 LibSQL 서버(`sqld`)로 전체 스택을 실행해 확인합니다. 운영 DB에는 연결하지 않습니다.

1. `sqld` 실행: libsql-server 릴리스의 `sqld --http-listen-addr 127.0.0.1:8080` (데이터 폴더는 저장소 밖에 둡니다)
2. 루트 `.env`(Git 제외) 작성: `SKYBASE_DB_ENDPOINT=http://127.0.0.1:8080`, `SKYBASE_DB_AUTH_TOKEN=local`, `SKYBASE_DB_NAMESPACE=local`, `BETTER_AUTH_URL=http://localhost:3100/api/auth`, `ALLOWED_ORIGINS=http://localhost:3100`
3. 마이그레이션 적용: `SKYBASE_DB_AUTH_TOKEN=local LOCAL_ADMIN_PASSWORD=<로컬 전용 비밀번호> node scripts/local-db.mjs`
   - localhost 엔드포인트만 허용하며, 비밀번호는 로컬 DB의 admin 계정에만 적용됩니다.
4. 개발 서버: `cd apps/client && LOVABLE_DEV_SERVER=true VITE_ENABLE_ROUTE_MESSAGING=true npx vite --host 127.0.0.1` → `http://127.0.0.1:3100` (IPv6가 없는 컨테이너에서는 `--host` 필요)
5. 검증: `pnpm lint`, `pnpm test`, `pnpm --filter client build`, `SERVER_BUILD_TARGET=web pnpm --filter server build`
   - 빌드로 생성된 `apps/server/dist/`는 커밋하지 않습니다(배포 흐름에서 생성).

## 8. 수정·배포 순서 (사용자 지정)

1. 수정은 먼저 로컬(작업 컨테이너)에서만 하고 lint·test·build와 로컬 실행으로 확인합니다. 브랜치에 커밋·푸시까지만 합니다.
2. 사용자가 화면으로 확인해야 하면 Vercel **미리보기 배포**(`vercel deploy`, `--prod` 없음)를 만들어 그 주소를 전달합니다. 운영 사이트(doogofood.site)는 바뀌지 않습니다.
3. 사용자가 "배포해줘"처럼 운영 배포를 명시적으로 요청할 때만 `vercel deploy --prod`를 실행합니다.
4. 운영 배포 후 서버 로그(`vercel logs`)로 주요 API 응답을 확인하고 보고합니다.
5. 배포는 기능(코드)만 반영합니다. 운영 상품 데이터(신규 등록·가격·삭제·가격변동 이력)는 관리자가 계속 바꾸므로 배포 과정에서 건드리지 않습니다.
   - 새 마이그레이션은 칸 추가처럼 기존 데이터를 바꾸지 않는 구조 변경만 허용합니다.
   - 기존 상품 값을 바꾸는 데이터 변경(카테고리 이동, 가격·상태 일괄 수정, 삭제 등)은 배포 전에 사용자에게 내용을 설명하고 명시적으로 허락받은 경우에만 넣습니다.
   - 배포 보고에 이번에 적용되는 마이그레이션과 "기존 데이터 변경 없음/있음"을 적습니다.
   - 테스트는 로컬 DB에서만 합니다. 미리보기 배포도 운영 DB를 쓰므로 미리보기에서 데이터를 바꾸는 테스트를 하지 않습니다.
